Engineering assessment · Planet Genesis

What's actually under the hood

A read of the whole codebase, with the performance claims measured against your real level rather than guessed at. One finding explains the lag you're feeling, and one architectural decision determines whether this can become a platform.

Reviewed 4 September 2026 Source 1 file · 270,770 bytes · ~4,400 lines Test level yours — 5 objects, 1,802 dabs Runtime Matter.js 0.19 · Canvas 2D · Artifact db

The prototype is in better shape than its history suggests. The core representation is unusual and it is the right unusual — it is what makes the game look hand-drawn rather than assembled from stamps. The rendering layer is genuinely well optimised. The physics quirks that took real work to find (Matter's _original mass trap, the group:0 collision-filter bug, the setParts double-shift) are all correctly worked around and commented. I would not rewrite any of it.

The lag is one function. Every brush dab you paint into an existing shape rebuilds that entire shape's physics body from scratch. On your level's largest object that costs 26 ms per dab — one and a half frames, for one dab. It gets worse the more you build, which is exactly backwards for a game about building.

The thing that will bite hardest later is saving. Every save creates a brand-new document instead of updating one — you already have two copies of the same level in the database, twelve seconds apart. There is no owner on a level, no version, no thumbnail, and levels are stored as one opaque JSON blob that will hit a hard size ceiling at roughly 11,000 dabs.

Nothing here is exploitable today, because there are no other users. Almost all of it is blocking before there are.

How it works

Everything follows from the dab

There is one architectural idea in this codebase and the rest is consequence. When you paint, the brush lays down small circles, squares or diamonds — dabs. Every dab is a real Matter.js body. All the dabs you paint in one continuous region are welded into a single compound body, an object. Painting near an existing object grows that object instead of starting a new one; that's the fusing you asked for, and it's why a level tends to be a handful of enormous objects rather than many small ones. Your level is 5 objects and 1,802 dabs; the largest single object holds 1,172 of them.

Rendering never draws dabs individually. Every dab in an object is traced into one path and filled once, so overlaps paint once and the silhouette reads as a single hand-drawn blob with no seams. Those paths are cached in the body's own coordinate frame and only rebuilt when the shape actually changes, so drawing your whole level costs 0.03 ms. That part is done properly and is not a concern.

The rest is layered on top: three depth layers with their own collision filters (only the middle one is interactive), a 16-pixel cellular water grid that falls, spreads and pools, density-based buoyancy that both kinds of water feed into, and a character system that stores drawings as normalised brush strokes rather than pixels.

The tension worth naming now: LittleBigPlanet stores a shape as a polygon with a handful of corners. Planet Genesis stores the same shape as a thousand circles. That choice buys the hand-drawn look and pays for it in physics cost, save size, and rebuild time — all three of the problems below are the same choice seen from different angles.

The lag

Why building gets slower the more you build

Adding a dab to an object calls rebuildCompound(), which discards the compound body and constructs a new one from every part — recomputing centroid, area, inertia and bounds, and touching the physics broadphase twice. That is the correct workaround for a real Matter bug, and it is fine when an object has thirty dabs. It is not fine at a thousand.

Because the object grows as you paint into it, a long stroke pays a rising cost per dab: the total work over one stroke grows with the square of its length. Erasing does the same thing — every pointer move rebuilds every object the eraser touched. Your largest object is already at 26 ms a dab.

The fix is small and low-risk: don't rebuild per dab. Accumulate the dabs for the whole stroke and rebuild once when you release the mouse — which is exactly what the drag-out shape tool already does, and why shapes feel instant while freehand doesn't. The shape stays frozen mid-stroke anyway (that's the drawing flag), so nothing needs correct physics until the stroke ends. This is a contained change to addPartToObject, paintAt and eraseAt, and I would want to do it before anything else.

Removing the rewind timeline just now also helped more than it looks: it was taking a full snapshot of every dab in the level 6.7 times a second, forever, in the background.

Health audit

Critical

Things that can lose work, corrupt state, or make the game unrecoverable.

Every save creates a new level

Data

doSave() calls db.collection("levels").add(...). There is no update path. Press save twice and you have two levels. Your database currently holds two 165 KB documents twelve seconds apart, both called "Untitled Level", both the same build — I pulled them to measure with.

Fix: give a level an id on first save and set() that document thereafter; "Save a copy" becomes an explicit action. Small change, and it has to happen before the level list becomes unusable.

A thrown error kills the game permanently

Recovery

The render loop reschedules itself on its last line. If anything above that line throws — a malformed level, an edge case in the water grid, a null body — the loop is never scheduled again and the game freezes with no error and no way back except a reload, losing anything since the last autosave.

Fix: wrap the frame body in try/catch and always reschedule; surface the error once instead of dying. Ten lines.

Loaded levels are trusted completely

Robustness

loadLevelData() takes x, y, r, shape and a material name straight from JSON into body construction. An unknown material throws on the first property read. A radius of NaN or 1e9 produces a broken body. A level claiming 500,000 dabs hangs the tab on load with no escape. Today this only matters if a save is corrupted; the moment anyone can hand you a level, it is the primary attack surface.

Fix: one validation function between JSON and the world — clamp numbers, reject unknown materials, cap total dabs, and fail with a readable message instead of a stack trace.

Levels have no owner and no identity

Architecture

A saved document is exactly { name, updatedAt, payload }. No id, no author, no version, no thumbnail, no published flag, no play count. The levels collection is shared by everyone who can open the artifact, so the moment you share it, all saves land in one bucket and anyone can delete anyone's work.

Fix: extend the document shape now, while there are two rows to migrate instead of two thousand. Cheap today, painful later.

The level format has a hard ceiling

Scale

Levels are stored as one JSON string of every dab — about 78 bytes each. Document stores of this kind cap a document at 1 MB, which puts the ceiling at roughly 11,000 dabs. You are at 1,802 and your level is not large. Someone who enjoys the brush will hit that wall, and they will hit it as a failed save.

Fix, in order: compact the encoding (a dab is five numbers, not five JSON keys — that alone is a 5–10× reduction), then split large levels across documents, then enforce a budget with a visible meter so it's never a surprise.

Worth watching

Not breaking anything yet. Each one gets harder to fix the longer it waits.

The object cap is on the wrong axis

Limits

PLACED_CAP limits the level to 1,500 objects. But fusing means an entire level can be three objects and fifty thousand dabs, so the cap never fires while the actual cost driver is unbounded. Cost tracks dabs, so the budget should too.

Characters and saved objects don't leave the browser

Sync

Levels sync to the cloud; My Characters, My Objects, keybinds and brush settings live only in localStorage. Same device, same browser, or they're gone. Players will notice this immediately and read it as data loss — because it is.

The autosave blocks the main thread

Performance

Every 15 seconds the game serialises the whole level and writes it to localStorage synchronously — about 2.8 ms combined on your level, scaling with size. It's a small stutter now and a large one on a big level. Skip the write when nothing changed, and move it off the interactive path.

The water grid is rebuilt from every dab, every step

Performance

rebuildWaterSolid() re-stamps every mid-layer dab into a 16-pixel grid up to three times per frame whenever any water exists. It's 0.42 ms on your level and it scales with dab count. It only needs redoing when something actually moved — the geomRev counter that already invalidates the render cache would do the same job here.

No level format versioning discipline

Compatibility

version: 2 exists and is checked, which is good instinct. But an older client meeting a v3 level falls through to the legacy branch and silently loads an empty world. Unknown versions should refuse loudly.

The creation tools assume a mouse

Reach

Pointer events mean touch mostly works, but there's no pinch-zoom, no touch equivalent of middle-drag, the personal menu is a fixed 26rem, and the character studio is a three-column full-screen layout that will be unusable on a phone. For a browser game where creation is the point, this decides how many people can create at all.

Leave it alone

Working systems whose imperfections don't justify the risk. I'd defend each of these.

The dab model and union-path rendering

Identity

This is the game. It's why a shape looks drawn rather than placed, and it can't be replaced with polygons without losing that. The costs it imposes are real and addressable without touching the idea.

The cached Path2D renderer

Performance

Per-object paths built once in the body's own frame, invalidated by an explicit revision counter. Correct, fast, and the reason a 1,800-dab level draws in 0.03 ms.

The Matter.js workarounds

Hard-won

The static-body mass trap, the collision-filter group:0 bug, the setParts double-shift, forces versus direct velocity damping in water. Each cost real debugging, each is commented with the reasoning. Touch them only with a failing test in hand.

The character art representation

Foundation

Drawings are lists of normalised brush strokes, resolution-independent, rasterised once and cached. This is already the right shape for everything you eventually want characters to do. Details below.

The water simulation

Working

A real cellular fluid model with compression and pressure, plus density-based buoyancy that both water types share. Expensive but correct, and correctness here was hard to reach.

The strategic question

Can this become a platform?

The game code can. The backend cannot, and it isn't close.

The artifact db is a document store the browser writes to directly. There is no server, so there is nowhere to put anything that must be true regardless of what a client claims. That rules out honest play counts, enforced ownership, rate limits, moderation, search ranking, and featured curation — a client can forge all of them. It is a fine place to keep your own levels. It is not a place to run a community.

So there is a fork ahead: at some point Planet Genesis stops being an artifact and becomes a web app with a real backend. That's not a rewrite of the game — it's one file with no framework, and it reaches persistence through about six functions. The move I'd make now, cheaply, is to put a thin storage layer in front of those six: saveLevel, loadLevel, listLevels, deleteLevel, and the same for characters. Everything else in the game calls that instead of touching db or localStorage directly. Then swapping the artifact store for a real API is one file, not a hunt.

That single change also fixes the character-sync problem, makes level ids natural, and gives thumbnails and metadata an obvious home. It's a couple of hours and it's the highest-leverage thing available.

The deeper move, when the time comes: separate what you draw from what you simulate. Keep dabs for rendering — they're cheap and cached and they're the look. But run the physics on a simplified outline of the same shape: tens of convex polygons instead of thousands of circles. Same appearance, a fraction of the physics cost, a fraction of the save size, and rebuildCompound stops being the bottleneck. It's a real project, not a weekend — convex decomposition of arbitrary blobs is fiddly and collision feel will shift slightly — but it's the one change that lifts every ceiling at once. I'd hold it until after the storage layer and the stroke-batching fix, and only if levels keep growing.

Creation

The editor, and what's actually missing

Against your list, the editor already has: drawing and placing, moving, rotating, copy/paste (duplicate), undo/redo, three layers, terrain, physics objects, hazards, collectibles, spawn points, checkpoints, decorations, backgrounds, saving, and instant playtesting. That is most of it, and the loop already closes.

What's genuinely absent, in the order I'd add it:

  • Test from here. Play should start at the camera, not the spawn flag. When you're building the end of a level, walking there every time is the single biggest tax on the create-test-edit loop, and this is a twenty-line change.
  • Publish as distinct from save. Right now they're the same act. Publishing should be the moment a thumbnail is captured, a version is frozen, and the level becomes visible to others.
  • Enemies. There are hazards, but nothing that moves and threatens. This is the largest gameplay gap against LittleBigPlanet and the thing most likely to make levels feel like levels.
  • Triggers and simple logic. Motor bolts are the first primitive. A button, a sensor, and a "when X then Y" link would open the door to the contraption-building that LBP levels are actually made of.
  • Scaling. Rotate and flip exist; resizing an object doesn't, and the dab model makes it awkward — you'd rescale every dab's position and radius. Worth doing, worth costing properly first.
  • Doors and portals. Cheap, and they change level structure more than their cost suggests.

I would not add all of these. Test-from-here and publish are small and unlock the loop. Enemies and triggers are the real content work.

The differentiator

Draw something, make it a game object

You asked whether this fits the architecture. It fits better than you'd expect — the two halves already exist and have never been introduced.

The character studio already turns freehand strokes into art. The shape tool already fills an arbitrary region with dabs by testing points against a mask: that's what insideShape does for a rectangle, ellipse or triangle. Swap that mask for a hand-drawn outline and you have "draw a shape, get a physical object" with no new architecture at all — you'd rasterise the drawn stroke to an offscreen canvas, read it back as a coverage mask, and run the same lattice fill inside it.

That gives you drawn platforms and drawn terrain almost immediately. Drawn enemies need the enemy system to exist first. Drawn decorations are nearly free — the decoration layers already ignore physics, so a drawn decoration is just a cached image on a layer.

My recommendation: don't build it yet, but when you do the enemy system and the publish flow, keep the seam in mind — an object should be able to come from a stroke source, not only from the brush.

Characters

The representation is already right

A character is { mode, color, size, frameCounts, sprites, rig, anchors }, where every drawing is a list of strokes in 0–1 coordinates. That means it renders crisply at any size, serialises to compact JSON, survives a round trip through the clipboard, and can be edited without ever being resampled. Whoever chose that chose well, and it's the right base for body/head/eyes/hair/clothing as separate drawn parts later — the rig mode is already that idea with four parts.

Three things it needs before characters can be shared:

  • It has to leave the browser. Same storage layer as levels.
  • It needs a size budget. Strokes are unbounded today; a character with a million points is a browser hang, and it will happen by accident before anyone does it on purpose.
  • It needs an id and an author, so a level can reference the character it was built around and a profile can list what someone has made.
Security

Nothing exploitable today. Most of it blocking before launch.

I want to be precise rather than alarming: there is no server, no accounts, and no other users, so there is currently almost no attack surface. Everything below is about the moment that changes.

  • Handled already: level names are escaped before going into the load list, which is the one obvious XSS path in the current code. Toasts use text nodes. There is no eval, no innerHTML on user data, and no file upload.
  • The main surface is level data itself. Hostile levels won't try to run code — they'll try to make your client do something catastrophic with numbers. Huge radii, NaN coordinates, absurd dab counts, deeply nested water arrays. Validation on load is the single most important control, and it belongs in the game, not the server, because the client is what gets hurt.
  • Client-authored anything is a claim, not a fact. Play counts, likes, level sizes and author names written by the browser can all be forged. When these matter, they have to be written by a server the player can't reach directly.
  • Ownership is unenforced. Shared collection, no owner field, so delete is available to anyone. This is the first thing a real backend must fix.
  • No rate limiting, no reporting, no moderation queue. All three are launch requirements, not nice-to-haves, and the reporting path should exist before the first stranger plays a level.
  • Levels as denial-of-service. Someone will publish a level engineered to freeze other people's browsers, for fun. Dab budgets, load-time validation, and a hard cap enforced at publish are the defence.
Roadmap

Prototype to public alpha

Reordered from your phases to match what's actually true here — the stability work is smaller than you'd expect and the backend work is larger.

Nowdays

Stop it being slow, stop it losing work

  • Batch the stroke rebuild — one physics rebuild per stroke instead of per dab. This is the lag.
  • Save updates instead of duplicating, and levels get an id.
  • The render loop can't die — try/catch and always reschedule.
  • Validate levels on load — clamp, reject, cap, fail readably.
  • Quiet the autosave — skip unchanged, get it off the interactive path.
Next1–2 weeks

The storage layer and the level format

  • One storage module every save and load goes through, for levels and characters alike.
  • Level format v3: id, author, version, timestamps, thumbnail, tags, published flag, stats — even where nothing reads them yet.
  • Compact the dab encoding. Five numbers, not five JSON keys; 5–10× smaller saves and faster loads.
  • Budget by dabs, not objects, with a visible meter so the ceiling is never a surprise.
  • Characters sync like levels do.
Then2–4 weeks

Close the creation loop

  • Test from here — play from the camera, not the spawn.
  • Publish as its own action, with a thumbnail captured at that moment.
  • Enemies — the biggest missing piece of the game itself.
  • A first trigger: button, sensor, and a link between them.
  • Make the tools work on a tablet, at minimum.

A real backend, and the social loop

  • Server-authored facts: play counts, likes, publish state.
  • Discovery: newest, popular, tags, search, featured.

Alphabefore strangers

Hardening

  • Rate limiting and abuse controls.
  • Error reporting — you need to see crashes you didn't cause.

  • Backups and a restore path for user levels. People will lose things.
  • Audio, VFX and loading polish — the parts that make it feel finished.

Four decisions I need from you

  1. Do I start with the lag fix? It's the smallest change with the biggest felt improvement, and it's contained. My recommendation is yes, immediately.
  2. How far away is "other people play this"? Months changes almost nothing about the order above. Weeks means the backend fork moves up and the editor work waits.
  3. Is this staying an Artifact for now? I'd keep it here through the next two phases — the constraint is useful and the game code stays portable either way. But I want to know if you're already picturing a real site.
  4. Enemies before or after publishing? Publishing makes the loop social. Enemies make the levels worth playing. I lean enemies first, because a discovery page full of levels with nothing in them is worse than no discovery page.
